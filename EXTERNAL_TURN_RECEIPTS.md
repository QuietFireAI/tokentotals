# External Turn Receipts

TokenTotals is not intended to replace the AI chat surface a person already uses.
The product acceptance target is:

> existing AI chat → normal provider answer → Turn Receipt directly beneath that answer

The local `/chat` route remains a controlled reference client and test harness. It does not satisfy the external-surface acceptance gate.

## Architecture

For provider-owned browser chats, the browser extension observes a completed assistant turn, derives a stable same-turn identity, sends only the telemetry/evidence available for that turn to the local TokenTotals engine, and receives server-rendered Turn Receipt HTML. The extension inserts that receipt as a sibling immediately after the provider answer. It does not append telemetry to or rewrite the provider response.

Receipt generation remains out-of-band from model generation. The browser extension does not make a second LLM call to generate or calculate a receipt.

## External-turn ingest

The local engine exposes:

```text
POST /api/external-turns/settle
POST /api/external-turns/settle/render
```

The external-turn contract is deliberately privacy-limited. The extension may pass visible current-turn text transiently so TokenTotals can derive local token estimates when provider-native token telemetry is unavailable. Prompt and answer text are not written to the Turn Receipt ledger. External conversation and turn identifiers are hashed before persistence.

If a provider surface exposes native usage fields, the adapter may submit those fields with an `observed` basis. Derived values stay labeled `derived`. Missing values remain unavailable; they are never converted to zero merely to complete a receipt.

## Consumer-web cost semantics

A consumer subscription/web chat is not assumed to have the same billing semantics as the provider's API. For `gemini_web`, `chatgpt_web`, and `claude_web`, TokenTotals currently leaves turn cost unavailable unless account/provider-native cost telemetry for that same transaction is actually observed.

Visible-text token estimates therefore do **not** imply a provider charge. Hidden system context, prior-thread context, internal reasoning, cache mechanics, tools, and account-specific billing dimensions may be unavailable to a browser adapter.

## Browser adapters

The extension currently contains selector chains for Gemini, ChatGPT, and Claude. These adapters are implementation candidates, not live-proof claims. Provider DOMs can change. A provider adapter is not considered proven until it survives a real completed turn in that provider's current authenticated web UI.

The extension baselines already-loaded messages and does not intentionally backfill an existing thread merely because the extension was loaded. New completed turns are settled after generation appears finished. When a provider-native turn/message ID is present it is preferred; otherwise the extension derives an opaque same-turn identity from the current thread and visible turn content.

## Standard and Expanded

A newly settled external receipt renders in Standard mode. Clicking the receipt toggles Standard and Expanded views using the same external turn identity. Expanded mode may include current thread aggregate data from the local ledger. No model call is made for either rendering mode.

## Failure behavior

If TokenTotals is not running, cannot settle the external turn, or lacks required evidence, the provider page continues to function. The extension shows a local receipt-unavailable state rather than modifying or blocking the provider answer.

## Proof gate

The external-surface product is not considered proven by source tests, CI, `/chat`, a mock page, or a screenshot generated by TokenTotals itself.

The acceptance gate requires a real external surface where one real user prompt produces one provider/agent answer and one Turn Receipt directly beneath that same answer, with:

- no second LLM call;
- provider answer unchanged;
- same-turn identity preserved;
- unavailable telemetry kept unavailable;
- Standard/Expanded rendering from the same canonical receipt;
- duplicate/reload/new-thread behavior not creating a false or cross-bound receipt;
- local ledger/export reconciliation for the receipt ID;
- provider UI continuing normally when the extension or local engine is disabled.

Until that live external proof exists, the browser integration is implemented/tested only to the level supported by its evidence.
